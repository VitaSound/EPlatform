# Геометрия wasm-канваса: DPR, масштаб поверхности и попадания мыши

Документ фиксирует состояние расследования «мышь попадает не туда / сверху пустое
место / полосы в заголовках» (клиент `crates/app`, ноябрь 2026). Написан так,
чтобы следующий человек (или модель) мог продолжить с этого места, не повторяя
диагностику. Отладочные инструменты **намеренно оставлены в коде** — см. §5.

---

## 1. TL;DR

Было четыре независимых дефекта, все — про пересчёт координат между браузером,
рендерером и GPU. Три исправлены полностью, четвёртый (полосы) тоже, но остаётся
вопрос по железу пользователя (§7).

| # | Симптом | Причина | Статус |
|---|---------|---------|--------|
| B1 | клик/hover срабатывает левее-выше курсора (на DPR ≠ 1) | `ui_scale` считался от `winit inner_size()`, который отдаёт то CSS-, то физические пиксели | исправлено `69a8781` |
| B2 | сразу после открытия страницы вся оболочка нарисована со сдвигом; после ресайза окна «лечится» | геометрия фиксировалась до раскладки канваса и не перепроверялась | исправлено `880188f` |
| B3 | при ширине окна > ~1360 CSS: пустая полоса над меню, ужатый layout-вьюпорт, уезжающие попадания | поверхность обрезалась до `max_texture_dimension_2d` (у пользователя 2048), а backing-стор канваса оставался больше | исправлено `3c4c931` + `7fe0771` |
| B4 | «полосатый» заголовок окна и фон тулбара при DPR 1.5 и обычных размерах | градиенты раскладывались полосками по 1 **логическому** пикселю → при `ui_scale = 1.5` полосы попадали на 1.5 физического | исправлено (см. историю, коммит «gradients in device pixels») |

Плюс отдельный измеренный факт (§3.5): если backing-стор канваса меньше его
CSS-бокса, браузер растягивает картинку, и 1 px линии превращаются в **полосы**.
Поэтому backing ≈ CSS × DPR — это не «оптимизация резкости», а условие отсутствия
артефактов.

## 2. Три системы координат

```
логические px (CSS)            раскладка: Qt-геометрия виджетов; 100 = 100
        │  ui_scale  (поверхностных px на логический px)
        ▼
поверхность, device px         текстура wgpu(= canvas.width/height = backing)
        │  css_box / backing   (браузер)
        ▼
экран, физические px           = CSS × devicePixelRatio
```

Обязательные инварианты (при их нарушении — ровно те симптомы, что были).
Зависят от **режима** рендера (§3.4):

| величина | смысл | инвариант |
|---|---|---|
| `canvas.width/height` | backing-стор = surface | всегда `==` сконфигурированной wgpu surface |
| режим 1 | `css×dpr ≤ max_dim` | `backing = round(css × dpr)`, `ui_scale ≈ dpr` |
| режим 2 | `css ≤ max_dim < css×dpr` | `backing = round(css)`, `ui_scale = 1` (браузер **равномерно** апскейлит; letterbox нет) |
| режим 3 | `css > max_dim` | CSS-бокс 100%; logical ужат (`layout_from_css=shrink`); `scale=1` (glyphon); letterbox **нет** |
| `ui_scale` | device px на логический px | `= surface / logical` при согласованной паре (не из `clamp/dpr`) |
| логический вьюпорт | раскладка виджетов | `= surface / ui_scale` ≡ используемый CSS |
| координата мыши | winit-web: `CSS × dpr` | `logical = raw / dpr` (**не** `/ ui_scale`) |

Когда logical == CSS раскладки — попадания точные. Резкость полная только в режиме 1.

`devicePixelRatio` (DPR) — количество физических пикселей на один CSS-пиксель:
100 % → 1.0, Windows 125 % → 1.25, 150 % → 1.5, iPhone → 3.0.

## 3. Карта кода и что где считается

### 3.1 Размер канваса — единственный источник правды: DOM

`crates/app/src/lib.rs`

- `App::dom_canvas_size()` (≈ стр. 563) — `getBoundingClientRect()` + `window.scale_factor()`.
  Возвращает `(css_w, css_h, dpr)`. `None`, если канвас ещё не в DOM/нулевой.
- `App::sync_canvas_geometry()` (≈ 4246) — вызывается **на каждом кадре**
  (`RedrawRequested`) и на первом движении мыши. Сверяет и, если надо,
  переконфигурирует:
  1. выбирает масштаб рендера по лимиту GPU (§3.4);
  2. `Gfx::apply_geometry(dpr, surface_w, surface_h, logical_w, logical_h)`;
  3. `App::sync_canvas_backing(w, h)` — `canvas.width/height`;
  4. при необходимости `App::resize_canvas_box()` — letterbox (§3.4, вариант 3).
  Ранний выход, если DPR не менялся и `last_size` совпадает (одно чтение DOM в
  установившемся режиме).
- `App::pointer_scale()` (≈ 4328) — то, на что делим координату winit: живой
  `window.scale_factor()` (= DPR), fallback `ui_scale()`. `ui_scale` тут
  использовать нельзя: после обрезки поверхности они различаются.
- `App::physical_size()` / `App::scaled_size()` — теперь только fallback для
  случая «канвас не в DOM» (на wasm помечены `#[allow(dead_code)]`).
- `WindowEvent::Resized` / `WindowEvent::ScaleFactorChanged` — на wasm просто
  вызывают `sync_canvas_geometry()`; на native сохранилось старое поведение.

`crates/app/src/gfx.rs`

- `fit_dimensions(w, h, max_dim)` — пропорциональное ужатие под лимит текстуры.
- `ui_scale_for(width, height, dpr, config)` — **из запрошенного** размера:
  `config.width / (width / dpr)` (с минимумом по двум осям).
- `Gfx::apply_geometry(dpr, w, h, logical_w, logical_h)` (≈ 320) — конфигурирует
  surface и считает `ui_scale = surface / logical`. Основной путь на wasm.
- `Gfx::resize(w, h)` (≈ 295) — native-путь; тоже считает `ui_scale` из
  **запрошенного** размера (иначе после обрезки логический вьюпорт ужимался).
- `Gfx::dpr()`, `Gfx::max_dim()`, `Gfx::size()` — геттеры для диагностики и
  `refresh_viewports`.
- `max_dim_override()` (≈ 121) — читает `window.__epMaxDim` (см. `?maxdim=` в §5).

`App::refresh_viewports()` (`lib.rs` ≈ 1253) — `floating/mdi` вьюпорты из
`gfx.size() / gfx.ui_scale()`. Отсюда раскладывается оболочка
(`Shell::central()` в `shell.rs` ≈ 471: меню + тулбар сверху, статус снизу).

### 3.2 Мышь и касания

`pointer_moved` (`lib.rs` ≈ 4338) и ветка `WindowEvent::Touch`:

```
sync_canvas_geometry();                 // самовосстановление размера/DPR
let scale = self.pointer_scale();       // = dpr
self.cursor = (x / scale, y / scale);   // логические px == CSS px
```

winit-web сам умножает `offsetX/offsetY` на `devicePixelRatio` — проверено
эмпирически (HUD: `winit=(238.5, 57.0)` при `client=(159, 38)` и DPR 1.5).

### 3.3 Отрисовка

`App::collect_paint()` собирает команды `rqt::gui::QPainter` в батчи
(`append_paint_commands`, `lib.rs` ≈ 3775). Логические координаты умножаются на
`ui_scale` при построении вершин в `gfx.rs`.

### 3.4 Раскладка по лимиту текстуры (три режима)

`max_texture_dimension_2d` — предел размера текстуры у драйвера. Обычно 8192–16384,
но за ANGLE/SwiftShader/виртуалкой бывает **2048** (случай пользователя: `gpu_max=2048`).

`sync_canvas_geometry()` выбирает:

1. **`css × dpr ≤ лимит`** → рендер в реальном DPR. Резко, окно занято полностью
   (`backing = css × dpr`, браузер ничего не масштабирует).
2. **`css ≤ лимит < css × dpr`** → рендер 1:1 по CSS (`backing = css`). Окно занято
   полностью, браузер растягивает один раз плавно: чуть мягче, но **без полос**.
   Это случай пользователя (окно 1707 CSS при лимите 2048).
3. **`css > лимит`** → канвас `100%` окна, logical ужимается
   (`logical = css * max_dim/max(css)`), `scale = 1`. Браузер апскейлит
   текстуру. **Не** снижать `ui_scale` ниже 1 — glyphon рисует белый/пустой
   текст. Пойнтер: `logical = (raw/dpr) * layout_from_css`.

Логический вьюпорт во всех трёх случаях остаётся равен CSS-боксу окна,
поэтому раскладка и попадания согласованы.

### 3.5 Почему нельзя давать браузеру масштабировать канвас

Измерено на реальном кадре: если `backing < css_box × dpr`, Chromium растягивает
канвас и 1 px линии (уже сглаженные дробным DPI) превращаются в **периодические
полосы**. Проверка: принудительно выставить `canvas.style.width = backing/dpr` —
полосы исчезают полностью, строка меню снова одна (row 32 = `172`).

Поэтому `backing == round(css × dpr)` — обязательное условие. Отсюда же режимы 1/3.

## 4. Журнал дефектов (что именно было не так)

### B1. Неверные единицы `inner_size()` (коммит `61ba7cd`, 25.11)

`physical_size()` умножал размер от winit на DPR, исходя из допущения «winit
отдаёт CSS-пиксели». winit 0.30 web пробрасывает `ResizeObserver`
(device-pixel content box), то есть величину, которая бывает **физической**.
Итог: backing и `ui_scale` разъезжались, и каждая координата пересчитывалась с
неверным коэффициентом — «мышь левее-выше». На DPR = 1 незаметно, поэтому
локально не воспроизводилось.

Исправление `69a8781`: размер берётся только из DOM
(`getBoundingClientRect() × dpr`), winit — лишь fallback.

### B2. Геометрия, зафиксированная до раскладки (коммит `880188f`)

Первый `Resized` мог прийти, когда канвас ещё не разложен (rect = 0), и
`last_size`/surface фиксировали неверный размер. Ничто не перепроверяло его до
следующего ресайза окна — отсюда «после ресайза всё нормально, сразу после
открытия адреса — нет».

Исправление: `sync_canvas_geometry()` на каждом кадре + на движении мыши.

### B3. Обрезка поверхности vs backing-стор (коммиты `3c4c931`, `7fe0771`)

Числа пользователя: `rect = 1438 × 645.3`, `dpr = 1.5`, `backing = 2157 × 968`,
а `viewport = 1365 × 613`. Второе — это `2048 × 919 / 1.5`, то есть поверхность
обрезалась до 2048 (`fit_dimensions`), а backing-стор оставался больше. Две беды:

- браузер растягивал меньшую поверхность в больший канвас → оболочка рисовалась
  не от угла (пустая полоса сверху);
- `ui_scale` считался от уже обрезанного размера → логический вьюпорт 1365
  вместо 1438 (раскладка/попадания плывут ~5 %).

Порог наблюдался как «ширина 1360» = `2048 / 1.5` — именно лимит текстуры,
делённый на DPR.

Исправление: `Gfx::apply_geometry`, backing = сконфигурированная поверхность,
`ui_scale` из запрошенного размера, мышь делится на DPR, плюс трёхуровневый
выбор масштаба (§3.4).

### B4. Градиенты в логических пикселях

`QPaintCommand::FillLinearGradientRect` разворачивался в полоски высотой **1
логический px** (`lib.rs`, ветка градиента). При `ui_scale = 1.5` каждая полоска
попадала на 1.5 физического пикселя → строки шли парами: `17, 16, 16, 16, 15,
15, 14, 14…` — визуально «полосатый» заголовок окна и фон тулбара (там градиент
`button → window`), а также вертикальные скроллбары.

Исправление: у команды появился флаг `horizontal` (в `gui.rs` —
`fill_horizontal_gradient_rect`, для «поперёк» вертикальных скроллбаров),
а раскладка в `append_paint_commands` идёт по **физическим** строкам/столбцам:
`y = device / scale`, толщина `1 / scale`. После фикса шаг ровный в каждой
строке: `17, 17, 16, 16, 16, 15, 15, 15, 14…`. Растеризатор страницы сравнения
(`rqt/src/raster.rs`, `fill_linear_gradient`) получил тот же флаг, чтобы PNG в
`client/review` не разъехались (проверено: медиана не изменилась).

## 5. Отладочные инструменты

**Удалены** из прод-клиента (HUD `?diag=1`, маркеры, `__epPtr` / `__epView` /
`__ptrLog` / `__epBuild`, URL `?maxdim=`). Регрессии геометрии ловятся
юнит-тестами `canvas_geometry` и ручной проверкой клика после resize.
Воспроизведение лимита текстуры — только через test hooks / feature, не через
URL на странице пользователя. См. [00-remove-diag.md](archive/completed-plans/agent-plans/00-remove-diag.md)
и [qt-parity-guide.md](qt-parity-guide.md).

Серверы (уже подняты в этой сессии):

```bash

cd client && python3 scripts/serve_dist.py --port 8080
cd client/review && python3 -m http.server 8125    # страница сравнения
```

Открывать:

```

```

Матрица проверок (все — «меню начинается с верхней кромки канваса, клик по
тулбару открывает следующую форму»):

| DPR | окно | ожидание |
|---|---|---|
| 1.0 | 1280×800 | `backing = 1280x800`, `scale=1.0` |
| 1.5 | 1280×800 | `backing = 1920x1200`, `scale=1.5` |
| 1.5 | 1707×907 | `backing = 2561x1361`, `scale=1.5` |
| 1.5 + `&maxdim=2048` | 1707×907 | `backing = 1707x907`, `scale=1.0` (мягче, без полос) |
| 1.5 + `&maxdim=1024` | 1707×907 | полный CSS 1707×907, `scale≈0.60`, `backing = 1024x544` |
| 1.5 + `&maxdim=2048` | 3000×1200 | режим 3: layout 3000×1200, `backing = 2048x819` (статусбар у низа окна) |

в области заголовка — значения должны меняться в **каждой** строке, без
повторяющихся пар (`17,17,16,16,16,15…`). Быстрый способ — сохранить PNG и
прогнать профиль (декодер PNG на stdlib, без зависимостей):

```python

python3 /tmp/rowscan.py shot.png 600
```

Регрессионные бейзлайны:

```bash

cd server && mix test                    # 30
cd client/crates/app && trunk build --release
cd client && python3 tools/formgen/review.py   # ~46 c, 212 форм
```

Ожидаемая статистика страницы сравнения после правок: **n=212, median 1.20,

исключением `172.25.21.226` в настройках прокси браузера или жёстким обновлением
в приватном окне.

## 7. Открытые вопросы и гипотезы (для следующей модели)

1. **`gpu_max = 2048` на машине пользователя.** Подтверждено его собственным HUD
   (и арифметикой `viewport = surface/1.5 = 2048/1.5 = 1365`). Причина — ANGLE /
   SwiftShader / виртуалка. Практический вывод: на широком окне клиент рисует в
   1× и браузер растягивает; это не баг клиента, а лимит железа.
2. **Остаточные круги/эллипсы.** Ветки `FillEllipse` / `StrokeEllipse` в
   `append_paint_commands` всё ещё раскладываются по **логическим** пикселям
   (`lib.rs`, рядом с градиентом). На DPR 1.5 индикаторы радио/чекбоксов могут
   давать ту же полосатость, что и градиенты. Кандидат на следующий фикс — тот же
   приём: итерация по физическим строкам/столбцам с шагом `1/scale`.
3. **Скачок резкости на пороге.** Переход режим 1 ↔ режим 2 происходит при
   `css × dpr > лимит`, то есть у пользователя при ширине 1365 CSS: окно шире —
   картинка мягче. Если это мешает, варианты: (а) всегда 1× на таком железе;
   (б) рисовать в промежуточную текстуру. Letterbox CSS-бокса отвергнут —
   статусбар переставал следовать за окном шире `max_dim`.
4. **Letterbox снят.** `resize_canvas_box(Some)` остаётся в коде на случай
   отката, но `choose_render_mode` больше не ставит `letterbox: true`.
5. **Возможная осцилляция на округлениях.** `sync_canvas_geometry` сравнивает
   `last_size` + `last_logical`; при дробном CSS-размере (например rect
   1707.0 при DPR 1.5 даёт 2560.5 → 2561) возможен «дребезг» на 1 px между
   кадрами. Наблюдением не подтверждён; если появится — заменить сравнение на
   допуск ±1 px.
6. **Текст в режиме 2.** По умолчанию шрифты считаются при `ui_scale = 1` и
   браузер апскейлит. Эксперимент резкости: `?texthd=1` или
   `window.__epTextHd = true` — glyphon metrics в масштабе DPR, `TextArea.scale`
   компенсирует размер. Выкл. по умолчанию (plan 42).
7. **Мобильный путь** проверялся только для `Touch` → `pointer_moved` (делитель
   `pointer_scale`). Отдельный вопрос — pinch-zoom (в `questions.md` F1:
   решено «пока не делать»).

## 8. Что менять нельзя (грабли)

- **Не** брать размер из `winit::inner_size()` как источник правды на wasm
  (единицы неоднозначны). Fallback до появления канваса в DOM — ок.
- **Не** выводить logical viewport как `clamped_surface / dpr`. Пара
  `(surface, logical)` задаётся режимом 1/2/3; `ui_scale = surface / logical`.
- **Не** делить координату мыши на `ui_scale` — только на `dpr` (winit-web).
- **Не** допускать `backing != surface`. Режим 1: `backing ≈ css×dpr`;
  режим 2: `backing ≈ css` **без** letterbox (равномерный апскейл ок);
  режим 3: полный CSS + сниженный `scale`, **без** letterbox CSS-бокса.
  Запрещён рассинхрон surface/backing (полосы §3.5).
- **Не** ужимать `canvas.style.width/height` ниже окна при `css > max_dim` —
  статусбар и chrome «залипают» на границе текстуры.
- **Не** раскладывать градиенты/скругления/эллипсы по логическим пикселям
  при дробном DPR — device-step или GPU-примитив
  ([qt-parity-guide.md](qt-parity-guide.md)).
- **Не** игнорировать `radius` у `FillLinearGradientRect` / `StrokeRoundedRect`.
- **Не** трогать `client/review/comments.md` при регенерации.
